> Redis 作为内存数据库，如果不能及时清理过期键，内存迟早会被撑爆。那它是怎么做到的？

## 先想一个问题

你在 Redis 里存了一个 key，设了 10 秒过期。10 秒后你用 `GET` 去读它，返回 nil —— 这个 key 已经没了。但如果一直不读它呢？它会赖在内存里不走吗？

这就是**过期策略**要解决的问题：既要及时删掉过期数据，又不能消耗太多 CPU 去检查。

Redis 的做法是用**惰性过期 + 定期过期**双剑合璧。

<!--more-->

## 三种过期策略

### 1. 定时过期

每个设置过期时间的 key 都创建一个定时器，到点就删。

| 优点 | 缺点 |
|------|------|
| 内存友好，过期即删 | CPU 不友好，大量定时器开销巨大 |

Redis **没有用**这个策略——对于高吞吐量的内存数据库来说，为每个 key 都开定时器是灾难。

### 2. 惰性过期（Lazy Expiration）

**只有当 key 被访问时才检查是否过期。**

```
客户端 GET mykey →
  Redis 检查 TTL:
    - 已过期 → 删除 key，返回 nil
    - 未过期 → 返回值
```

- **优点**：CPU 友好，只在访问时才检查
- **致命缺点**：如果 key 过期后再也没有被访问，它就**永远占着内存**。我们称这些为"冷过期数据"。

### 3. 定期过期（Periodic / Active Expiration）

这就是补惰性过期的短板。Redis 会在后台**定时随机抽查**一批带 TTL 的 key，发现过期的就删掉。

**Active Expire Cycle 算法**（默认每秒执行 10 次，由 `hz` 参数控制）：

```
1. 从带 TTL 的 key 集合中随机抽取 20 个
2. 删除其中所有过期的 key
3. 如果这 20 个 key 中过期比例 > 25%（即 ≥5 个）：
   → 回到步骤 1，继续清理
4. 如果过期比例 ≤ 25%：
   → 本轮结束，等下一次触发
```

这里的 `25%` 阈值很精妙：
- 过期率高 → 说明堆积严重 → 继续循环，加大清理力度
- 过期率低 → 说明够干净了 → 收手，避免空转 CPU

> 从 Redis 6 开始，带 TTL 的 key 用 radix tree 存储，定期过期可以更高效地定位"快过期"的 key。

## 双剑合璧：惰性 + 定期

画个图理清关系：

```
Key 过期后的命运：
                         ┌→ 正好被客户端读取 → 惰性检查 → 删除 ✓
key TTL 到期 →           │
                         └→ 没人读 → 定期抽查抽中 → 删除 ✓
                                    └→ 没抽中 → 继续占内存（等待下次抽查）
```

这就是为什么 Redis 不能保证 key 在过期瞬间就被删除——但能保证**最终会被清掉**。

## 过期 ≠ 淘汰

很多人把"过期"和"淘汰"混为一谈，但它们完全不是一回事：

| 维度 | 过期（Expiration） | 淘汰（Eviction） |
|------|-------------------|-----------------|
| **触发条件** | Key 的 TTL 到期 | 内存超过 `maxmemory` 上限 |
| **处理方式** | 惰性 + 定期 | 按策略选 key 驱逐 |
| **目标** | 删除过期无用数据 | 为新数据腾空间 |
| **生效范围** | 仅带 TTL 的 key | 可作用于任意 key |

常见的淘汰策略（`maxmemory-policy`）：

| 策略 | 范围 | 行为 |
|------|------|------|
| `noeviction` | - | 内存满时直接报错，不淘汰 |
| `allkeys-lru` | 所有 key | 淘汰最近最少用的 |
| `allkeys-lfu` | 所有 key | 淘汰最不常用的 |
| `volatile-lru` | 仅带 TTL | 淘汰最近最少用的 |
| `volatile-lfu` | 仅带 TTL | 淘汰最不常用的 |
| `volatile-ttl` | 仅带 TTL | 淘汰 TTL 最短的 |

**一句话总结**：过期是"这个数据该删了"，淘汰是"内存不够了，总得赶走谁"。

## 总结

- Redis 用**惰性过期**（访问时检查）+ **定期过期**（后台随机抽查，25% 阈值循环）来处理 key 过期
- 当内存满时，由**淘汰策略**（LRU/LFU/TTL/noeviction）决定驱逐谁
- 过期和淘汰是不同的机制，别搞混
- 定期过期的自适应性让它"忙时多清理，闲时少浪费"，很优雅
